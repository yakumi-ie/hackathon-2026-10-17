# よりみち

「動画のつづきは、街で。」
現在地の近くで、ニコニコ動画に登場した景色や体験を見つけるハッカソン用プロトタイプ。
スマートフォンを中心に、近くの地点を地図で確認し、動画カードをスクロールして視聴と経路検索へ進める。

## 起動

Node.js 22.12 以上を使用する。

```sh
npm run deps
npm run dev
```

http://localhost:3000/ を開く。
Docker Sandbox 内で起動した場合、ホストのブラウザから開くにはポート転送が必要。
Mac 側のターミナルで次を実行する（今回のサンドボックス名は `dw-hackathon`）。

```sh
sbx ports dw-hackathon --publish 3000:3000
```

転送後は http://127.0.0.1:3000/ を開く。
ポート転送の設定は [sbx ports の公式ドキュメント](https://docs.docker.com/reference/cli/sbx/ports/) を参照。

初回表示でブラウザの位置情報取得を試み、成功したら現在地の近くの動画を表示する。
取得待ちの間は上野駅のデモを表示し、拒否・取得失敗・10 秒のタイムアウト時もデモで続けられる。
「現在地」で再取得できる。
上野・浅草・東京・横浜・鎌倉のデモ地点を選べる。
取得中にデモ地点を選んだ場合は、その選択を優先する。

下部に固定した徒歩 / 車のセレクターで、一覧を眺めながら検索範囲を変えられる。
徒歩は半径 1 km、車は半径 10 km の直線距離で検索する。
localhost 以外では HTTPS が必要なため、スマートフォンから LAN の HTTP アドレスで開いた場合はデモ地点を使う。

## データ

[共有された動画旅マップ](https://www.google.com/maps/d/viewer?mid=13Xyxidjdp-PCcwAl2zI76WBqUSOKkX95) の KML から、関東周辺の 349 本・882 地点を収録。
抽出範囲は東経 139〜141 度、北緯 35〜36.5 度で、関東全域を網羅するものではない。
同じ動画の複数地点は一つのカードに集約し、最寄りの地点の距離で並べる。

アプリ内の地図には、現在の検索範囲に入る地点だけを表示する。
背景地図は OpenStreetMap、表示は Leaflet を使用する。
初期表示はコンパクトにし、「大きく見る」や地点選択で広げる。
ピンと動画カードは共通の番号で結び、同じ座標の複数動画は一つのピンにまとめる。
近接したピンは青い丸に集約し、選ぶと拡大する。
青い丸の数字は、まとめたピンの数を表す。
カードの「地図で見る」で地点へ移動し、ピンから対応するカードへ戻れる。
動画一覧は最初に 8 本を表示し、末尾が近づくと次の 8 本を追加する。
「さらに動画を見る」ボタンでも追加でき、サムネイルも遅延読み込みする。
地図には最初から検索結果すべての地点を表示し、未表示の動画をピンから選ぶと、そのカードまで追加して移動する。
検索地点や徒歩 / 車を変更すると、一覧の表示件数をリセットする。
地図上でもホイール操作でページをスクロールできる。

地点名は元マップに紐づく Google の施設 ID から補完し、ピン・カード・追加地点の一覧へ表示する。
施設 ID に一致する名称だけを採用し、近隣施設からの推測は行わない。
名称を確認できない地点は「マップ掲載地点」と表示する。
現在は 162 種類の名称を 201 地点へ補完している。
Google 側の取得回数制限により、施設 ID があっても名称未取得の地点がある。
座標をそのまま経路検索に使う。
Google マップへ移動手段・出発地点・目的地点を渡す。
動画はニコニコ動画で開く。
サムネイルはニコニコの公開 `getthumbinfo` API を元に、大きいサイズ（`.L`）の画像 URL を静的データへ取り込む。
Google マップの画像には依存しない。
削除済みなどでサムネイルを取得できない動画は代替表示にする。

更新には Python 3 の標準ライブラリだけを使う。

```sh
python3 scripts/import-map.py
python3 scripts/place_names.py --limit 30
```

名称は `scripts/place-names.json` に保存し、次回の取り込みでも再利用する。
名称収集は同時実行を防ぎ、未取得の施設を掲載地点数の多い順に調べる。
問い合わせは直列で最低 8 秒間隔、1 回の実行では既定で最大 30 施設に制限する。
元マップは 24 時間、名称が確認できなかった施設は 7 日間キャッシュする。
HTTP 429 / 403 やアクセス制限画面を受けたら停止し、最低 1 時間の待機期限を保存する。
`Retry-After` がある場合はその期限も守り、制限が続く場合は待機を延ばす。
通信障害・HTTP 5xx は最低 5 分間停止し、応答形式の変更でも取得を停止する。
実行をやり直しても取得間隔と待機期限を引き継ぎ、確認済みの名称を保持する。
IP の変更や CAPTCHA の回避は行わない。

保存済みの待機期限を待ってから、件数を限定して再開する場合：

```sh
python3 scripts/place_names.py --wait --limit 40
```

`--refresh-source` を付けると元マップのキャッシュを更新する。
取得間隔・待機期限・未確認施設のキャッシュは `artifacts/place-name-*.json` に保存する。
2026-10-17 の再収集では最初の問い合わせが HTTP 429 となり、201 地点の名称を保持して待機へ移った。
元マップの表示データと Google マップの公開表示情報を使うため、名称の更新処理はこれらの形式に依存する。
実行時のアプリには名称を含めた静的データを配信し、施設情報 API へのアクセスは不要。

## ビルドと配信

```sh
npm run typecheck
npm run build
npm run preview
```

TanStack Start のプリレンダリングで生成した `dist/client` を静的配信できる。
ランタイムの API サーバーやデータベースは不要。
`dist/server` も生成されるが、プリレンダリングで使うビルド出力であり、静的配信時にはアップロードしない。

### Cloudflare Drop

[Cloudflare Drop](https://developers.cloudflare.com/changelog/post/2026-07-08-cloudflare-drag-and-drop/) へは `dist/client` フォルダーをアップロードする。
ZIP を使う場合も、ルートに `index.html` と `assets/` がある構成にする。
ブラウザで位置情報取得と近隣検索を行い、背景地図とサムネイルはそれぞれ OpenStreetMap とニコニコから取得する。
Workers のサーバースクリプトや Node.js の実行環境は不要。

### GitHub Release

GitHub の **Actions → Build static release → Run workflow** から、リリースを作成できる。
選択したブランチ / コミットをビルドし、Release とタグを作成する。

- `version` に `1.2.3` または `v1.2.3` を指定すると、`v1.2.3` を作成する。
- 未指定なら、最新の正式な `vX.Y.Z` タグから patch を 1 つ上げる（例：`v1.2.9` → `v1.2.10`）。
  正式なタグがまだなければ `v0.0.1` にする。
- 指定したタグが別のコミットに付いている場合は、上書きせずに終了する。

型チェックとビルドを行い、`dist/client` のみをまとめた `yorimichi-drop.zip` を Release に添付する。
Release の ZIP をダウンロードして、そのまま Cloudflare Drop にアップロードできる。
`dist/server` や `node_modules` は ZIP に含めない。

`v*` のタグを push した場合も、そのタグのリリースを作成する。

```sh
git tag v0.1.0
git push origin v0.1.0
```

依存パッケージは lockfile の確定済みバージョンをインストールする。
同じタグのワークフローを再実行した場合は、既存 Release の ZIP を更新する。

### コンテナ

Alpine Linux のコンテナ用に Dockerfile と nginx の設定を用意している。
SSL 終端はインフラ側で行う。

```sh
docker build -t yorimichi .
docker run --rm -p 8080:8080 yorimichi
```

## 依存パッケージの待機期間

`pnpm-workspace.yaml` に `minimumReleaseAge: 10080`（1 週間）を設定している。
今回の環境では指定の pnpmInstall MCP がこのリポジトリにアクセスできないため、npm と package-lock.json を使用する。
`npm run deps` でも、実行時から 1 週間前の公開日時を上限にしてインストールする。
コンテナのビルドには確定済みの lockfile を使う。

実装計画は [PLAN.md](PLAN.md) を参照。
発表資料は [Marp スライド](docs/presentation.md)、時間配分とデモ手順は [発表ガイド](docs/README.md) を参照。

## 確認済みの動作

型チェック、本番ビルド、生成された静的ファイルの配信で動作を確認した。
Chrome のスマートフォン相当の画面幅とデスクトップ幅で、以下を確認している。

- 徒歩 / 車の検索範囲と、動画・経路へのリンク。
- 上野駅の徒歩圏で 11 本、車の範囲で 47 本の表示。
- 抽出した地点だけの地図、近接ピンの集約、ピンとカードの相互移動。
- 8 本から始まる動画一覧と、スクロールによる全件表示（車：8 → 16 → 24 → 32 → 40 → 47 本）。
- 未表示の動画へのピンからの移動、手動追加、検索条件変更時の一覧リセット。
- 位置情報の取得成功、拒否、未収録地域の結果なし表示。
- 取得中にデモ地点へ切り替えた場合、後から届く位置情報で上書きされないこと。

位置情報の成功・拒否はブラウザの開発者機能で再現して確認した。
スマートフォン実機での測位と、Docker コンテナの起動は未確認。
Playwright でホストの開発サーバーに接続し、320〜1920 px の幅でカードの重なりがないことと、ニコニコのサムネイル・OpenStreetMap の実表示を確認した。
地図上のホイール操作、同じ地点の再選択、位置情報の取得中の地点変更、画像・背景地図の取得失敗も確認した。
名称収集の取得間隔、制限時の停止と待機期限、キャッシュ、施設 ID の照合、既存名称の保持は、通信を模擬して確認した。
初回の位置取得と失敗時のデモ表示、コンパクトな地図の拡大、下部の移動手段選択を確認した。
320 / 375 / 390 px の画面で、スクロール前に最初の動画サムネイルが見えることも確認した。
依存パッケージの監査は脆弱性 0 件で、lockfile の全パッケージが公開から 1 週間以上経過していることを確認した。
